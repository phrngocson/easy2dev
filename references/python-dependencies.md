# Reproducible Python dependencies

Use this policy whenever a Python application adds, removes, installs, validates, packages, or deploys dependencies.

## New projects: uv is canonical

For a new Python backend, keep exactly one human-owned dependency manifest and one machine-owned lock:

- `pyproject.toml` declares direct runtime and development dependencies, Python compatibility, and project metadata.
- `uv.lock` records the complete resolved dependency graph and exact versions.
- `uv sync --locked` recreates the environment without changing the lock.

Change dependencies only through the project manager:

```powershell
uv add <package>
uv add --dev <package>
uv remove <package>
uv sync --locked
```

Commit `pyproject.toml` and `uv.lock` together. Rebuild affected containers and rerun the consumer test after any dependency change. Never treat bare `pip install <package>` or `uv pip install <package>` as a durable project change; a package present only in `.venv`, a global interpreter, a cache, or an old image layer is undeclared.

Make `scripts/dev.ps1`, Docker builds, and CI use `uv sync --locked`. Run `uv lock --check` in CI or the equivalent checked path before tests. Do not let daily startup regenerate `uv.lock`.

## Export requirements only for a real consumer

Do not create `requirements.txt` for familiarity. Create it only when a named deploy platform or legacy build interface accepts pip requirements but cannot consume uv.

Generate the production dependency artifact from the existing lock, never by hand or from `pip freeze`:

```powershell
uv export --locked --format requirements.txt --no-dev --no-emit-project --no-header --output-file requirements.txt
```

Prepend this marker:

```text
# Generated by Easy2Dev from uv.lock. Do not edit.
```

Keep `pyproject.toml` and `uv.lock` canonical. CI must rerun the fixed export into a temporary file and compare its normalized body with the committed artifact. A changed, stale, orphaned, or unmarked `requirements.txt` beside a uv project is `FAIL` because dependency ownership is ambiguous.

The deploy adapter may use `python -m pip install -r requirements.txt` only for this generated artifact. It must not add packages outside the artifact. Prefer installing the application source separately rather than emitting the local project into the exported dependency list.

## Existing pip projects: preserve, validate, propose

Do not silently migrate an existing repository whose canonical source is `requirements.txt`. First preserve its Docker, CI, and deployment workflow and validate all recursively included `-r`/`--requirement` and `-c`/`--constraint` files.

Accept the legacy dependency set only when:

- every included file exists inside the repository;
- every registry package uses an exact `==` version without a wildcard;
- every Git dependency is pinned to a commit hash;
- every remote archive has a cryptographic hash;
- the canonical startup path installs with `python -m pip install -r requirements.txt` inside an isolated virtual environment;
- `dev.ps1` recreates that environment when the requirements checksum changes, or uses an equivalent exact synchronization tool;
- CI installs into a clean environment before running tests and builds.

Unpinned packages, local machine paths, missing include files, floating Git branches/tags, or packages installed outside the declared set are `FAIL`.

After establishing current behavior, present a scoped migration plan to `pyproject.toml + uv.lock`. Migration changes package ownership, Docker, CI, and deployment behavior, so wait for explicit approval before performing it.

## Evidence

Report dependency gates separately:

1. source ownership: uv, generated export, or validated legacy pip;
2. lock/pin integrity;
3. canonical frozen synchronization;
4. generated export drift when applicable;
5. clean-environment install;
6. affected tests, image build, and runtime smoke.

Static declarations do not prove a clean install. A passing build from a populated environment does not prove reproducibility.
